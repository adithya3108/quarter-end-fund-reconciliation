# Decisions

## Decision 1: The LLM categorizes, and code checks every answer, without a silent fallback
**Decision:** The bank agent sends the whole statement to the LLM in one call (each row gets an index, and the 30 Sep liabilities are included as context), then checks every answer in code. The category must be allowed and match the cash direction (a capital call can't be a debit). The LP code must have a valid format. Purchases and sales must name a company. Invalid answers are asked again individually, with the reason. If an answer is still invalid, the run stops with an error. Separately, a deterministic keyword reader categorizes every row, and any disagreement is marked `needs_review` and printed. The LLM's answer is kept, not overwritten.
**Alternatives:** (a) Trust the LLM output as it comes back. (b) Use keyword rules only, with no LLM. (c) Fall back to the rules whenever the LLM disagrees.
**Why:** (a) lets a single wrong label move the NAV without anyone noticing. (b) breaks the brief's requirement and doesn't carry over to other banks' wording. (c) would let the rules quietly make the decisions. Keeping the LLM as the decision-maker, code as the guardrail, and disagreements visible to a human is how I'd want a real close to run. The NAV bridge acts as a final check: an accrual settlement booked as an expense shows up as a non-zero difference.

## Decision 2: Read the PDF by word position, not as text and not with the LLM
**Decision:** Use pdfplumber word coordinates. On each page, the column boundaries come from the header row. Amounts are assigned to Debit, Credit or Balance by their right edge, because the numbers are right-aligned. Lines without a date are joined to the description of the row above, but only if they sit close underneath it, which keeps footers out. Afterwards, every running balance, the closing balance and the printed period totals are checked to the cent.
**Alternatives:** Split `pdftotext` output on spaces, or ask the LLM to read the PDF.
**Why:** Half of the rows have no reference, so splitting text can't reliably tell a credit from a debit. An LLM reading numbers is the place most likely to introduce a silent error. Position-based parsing is deterministic, and the balance checks prove it read every number correctly.

## Decision 3: A small standard-library A2A implementation, with Agent B releasing marks only after matching
**Decision:** Each agent runs on Python's `ThreadingHTTPServer`, serving its agent card at `/.well-known/agent-card.json` and JSON-RPC `message/send` at `/a2a`. Tasks are kept in memory, so the second message continues the same `taskId`/`contextId`. Agent B matches company names ignoring case and punctuation ("FJORD PAYMENTS AS" equals "Fjord Payments AS"), and matches dates and amounts exactly to the cent. Each of its records can only be matched once, so extra or duplicate items fail. NAV is a second skill on Agent B, called with Agent A's ledger. All A↔B traffic is written to `a2a_log.jsonl`. The orchestrator's own calls go to a separate log so that the A↔B log shows only the four-message conversation.
**Alternatives:** The `a2a-sdk` package, or FastAPI/uvicorn.
**Why:** The exercise only uses `message/send`, and the reviewers run the code on their own machine. Using the standard library means two fewer dependencies to install and version-match. Every line of the protocol fits in one file I can explain, and the A2A tests run against real HTTP on local ports. The trade-off is that I implement only part of the spec (see the README gaps).
